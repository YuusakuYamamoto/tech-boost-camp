# ADR-0015: シークレット注入はホストの起動スクリプトで行う

- **Status**: Proposed
- **Date**: 2026-04-25
- **Deciders**: Yusaku

> **改訂（2026-10-15）**: ADR-0001 の改訂（Container Instances → Compute VM + Docker Compose）に伴い、全面的に書き換えた。当初はコンテナのエントリポイントスクリプトで Vault から取得する方式を定めていたが、実行基盤が VM になったことで前提が変わっている。

## Context

アプリケーションの実行時シークレット（DB パスワード、Google OAuth のクライアントシークレット、セッションシークレット）は OCI Vault に格納する（ADR-0014）。これをコンテナに届ける方式を決める必要がある。

アプリは Compute VM 上の Docker Compose で実行する（ADR-0001）。VM にはインスタンスプリンシパルが付与され、Vault への読み取り権限を持つ（ADR-0022）。

選択肢：

- **A. ホストの起動スクリプトが取得し `.env` に書き出す**: VM の bootstrap が Vault から取得して `.env` を生成し、Compose がそれを読む
- **B. コンテナのエントリポイントが起動時に取得する**: イメージに OCI CLI を含め、コンテナ内でインスタンスプリンシパル認証を行う
- **C. アプリコードが起動時に Vault から取得する**: アプリに OCI SDK を導入する

## Decision

**パターン A（ホストの起動スクリプトでの取得）** を採用する。

具体的には：

- VM の起動スクリプトが `OCI_CLI_AUTH=instance_principal` で Vault からシークレットを取得する
- 取得した値を `/opt/tbcamp-app/.env` に書き出す（パーミッションは `600`、所有者 `root`）
- `docker-compose.yml` の `env_file` でこのファイルを参照する
- アプリ側のコードは通常の環境変数を読むだけ（クラウド非依存）

**`modules/postgres_vm/` が DB パスワードに対して行っている処理と同じ形**である。`scripts/bootstrap-postgres.sh` が Vault から取得して `/opt/postgres/.env` に書き出し、PostgreSQL コンテナ自身は OCI の資格情報を持たない。

### コンテナに資格情報を持たせない

この方式の結果として、**アプリケーションのコンテナはインスタンスプリンシパルを使わない**。OCI CLI も OCI SDK も不要である。

アプリは LB 経由でインターネットに公開されるため、侵害の可能性を前提に置く必要がある。コンテナが資格情報を持たなければ、侵害されても Vault や Object Storage には到達できない。到達するにはホスト自体の掌握（コンテナエスケープまたは SSH）が必要になる。

## Alternatives Considered

### B. コンテナのエントリポイントが起動時に取得する（当初の決定）

Container Instances には ECS Fargate の `secrets` フィールドのような機能がなく、Vault 連携のネイティブサポートがイメージ pull 認証に限定されていたため、当初はこの方式を採用していた。

- **不採用理由**:
  - 実行基盤を Compute VM に変更したため、ホスト側で取得する経路が使えるようになった
  - コンテナイメージに OCI CLI を含める必要がなくなり、イメージサイズ（約 50MB）と保守の手間が減る
  - コンテナに資格情報を持たせないほうが、侵害時の影響範囲が小さい
  - `postgres_vm` と実装を揃えられる

### C. アプリコードが起動時に Vault から取得する

- **不採用理由**:
  - アプリが OCI 依存になり、別クラウドへの移植時に修正が必要
  - ローカル開発時の挙動と本番の挙動に差分が生じる
  - 新しい依存パッケージ（OCI SDK）が増える

### デプロイ時に平文の環境変数として渡す

- **不採用理由**:
  - Container Instances ではシークレットの平文値がインスタンスの設定に焼き込まれ、`describe` 結果に表示される問題があった
  - Compute VM の場合はこの問題は生じないが、デプロイ経路（CI のログ、Compose ファイル）に値が流れるため採らない

## Consequences

### Positive

- アプリコードはクラウド非依存のまま保てる
- ローカル開発は通常の `.env` ファイルで動作可能
- コンテナイメージに OCI CLI を含める必要がない
- `postgres_vm` と同じ仕組みのため、2 箇所で型が共通になる
- アプリのコンテナが侵害されても、クラウドの資格情報には到達できない

### Negative / Trade-off

- シークレットをローテーションした際、VM 上で `.env` を再生成してコンテナを再作成する必要がある（`systemctl restart` で完結する）
- `.env` が VM のファイルシステム上に平文で存在する。パーミッションで保護するが、ホストを掌握されれば読める
- VM の起動スクリプトが Vault に依存するため、Vault への到達性がないとアプリが起動しない

### Neutral

- Vault への経路は Service Gateway を通る（NAT Gateway の従量課金に影響しない）
- 将来 Container Instances に戻る場合は、パターン B に切り替えることになる。その際はイメージ側の変更が必要
