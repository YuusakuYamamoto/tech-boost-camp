# ADR-0004: 単一 VCN によるネットワーク基盤

- **Status**: Proposed
- **Date**: 2026-04-25
- **Deciders**: Yusaku

## Context

本アプリのインフラリソース（Container Instance、PostgreSQL VM、LB）を配置するためのネットワーク基盤を設計する必要がある。本アプリは個人プロジェクトで、他のアプリと同居する予定はないが、

- パブリック / プライベートのサブネット分離
- セキュリティグループ・経路制御
- 外部送信用ゲートウェイ（Service Gateway / NAT Gateway）

の構成を決める必要がある。

## Decision

**単一 VCN** を立て、その中に必要なサブネット・ゲートウェイを配置する。

### 構成

| リソース             | 内容                                                       |
| -------------------- | ---------------------------------------------------------- |
| VCN                  | 1 つ（CIDR 例: 10.0.0.0/16）                               |
| パブリックサブネット | LB を配置（CIDR 例: 10.0.1.0/24）                          |
| プライベートサブネット | Container Instance / PostgreSQL VM を配置（10.0.2.0/24） |
| Internet Gateway     | LB がパブリック IP で受信するため必要                      |
| Service Gateway      | OCIR / Vault / Object Storage / Oracle Linux ミラーへの経路 |
| NAT Gateway          | **必要**（Docker Hub からの PostgreSQL イメージ取得用） |

OS パッチは Service Gateway 経由（無料）で取得する。NAT Gateway は Docker Hub への通信（postgres イメージ pull）に限定して使用する。

OCI の NAT Gateway は固定費ではなく従量課金（$0.0025/GB のデータ処理料）。postgres イメージ pull 程度なら月数セント以下の見込みで、コスト目標（月数ドル）の範囲内に収まる。

## Alternatives Considered

### OCIR に PostgreSQL イメージを事前プッシュして NAT Gateway を回避

- **不採用理由**:
  - OCIR への postgres ベースイメージの手動プッシュ・バージョン管理が運用負荷になる
  - postgres の公式イメージ更新のたびに OCIR への再プッシュが必要（CI に組み込むか手動か）
  - NAT Gateway の実費が月数セント以下で無視できるレベルであれば、運用複雑化より NAT GW を立てる方が合理的

### Container Instance / VM をパブリックサブネットに直接配置

- **不採用理由**:
  - インスタンスに直接インターネットからアクセス可能になり、セキュリティリスクが増加
  - LB を前段に置く意義が薄れる

## Consequences

### Positive

- 一般的な「LB はパブリック / アプリ・DB はプライベート」のパターンを踏襲しており、セキュリティ的にも素直
- Service Gateway は無料。OS パッチ・OCI 内サービス通信は引き続き Service Gateway 経由で課金ゼロ
- NAT Gateway が利用可能になることで、将来的な外部 API 連携も追加費用最小で対応できる

### Negative / Trade-off

- NAT Gateway の従量課金が加わる（$0.0025/GB。Docker イメージ pull 程度なら月数セント以下の見込み）
- プライベートサブネットからのインターネットアクセス経路が生まれるため、NSG のルール管理が重要になる

### Neutral

- VCN の CIDR は将来的にサブネットを追加できるよう /16 で確保しておく
