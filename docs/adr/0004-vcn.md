# ADR-0004: 単一 VCN によるネットワーク基盤

- **Status**: Proposed
- **Date**: 2026-04-25
- **Deciders**: Yusaku

## Context

本アプリのインフラリソース（Container Instance、PostgreSQL VM、LB）を配置するためのネットワーク基盤を設計する必要がある。本アプリは個人プロジェクトで、他のアプリと同居する予定はないが、

- パブリック / プライベートのサブネット分離
- セキュリティグループ・経路制御
- 外部送信用ゲートウェイ（Service Gateway / NAT Gateway）

の構成を決める必要がある。

## Decision

**単一 VCN** を立て、その中に必要なサブネット・ゲートウェイを配置する。

### 構成

| リソース             | 内容                                                       |
| -------------------- | ---------------------------------------------------------- |
| VCN                  | 1 つ（CIDR 例: 10.0.0.0/16）                               |
| パブリックサブネット | LB を配置（CIDR 例: 10.0.1.0/24）                          |
| プライベートサブネット | Container Instance / PostgreSQL VM を配置（10.0.2.0/24） |
| Internet Gateway     | LB がパブリック IP で受信するため必要                      |
| Service Gateway      | OCIR / Vault / Object Storage / Oracle Linux ミラーへの経路 |
| NAT Gateway          | **必要**（プライベートサブネットから外部インターネットへのアウトバウンド） |

OS パッチと Oracle サービス宛の通信は Service Gateway 経由（無料）で取得する。NAT Gateway の導入動機は Docker Hub からの PostgreSQL イメージ取得だが、**宛先を Docker Hub に限定する制御は入れていない**。プライベートサブネットからの Oracle サービス宛以外の全アウトバウンド通信が NAT Gateway を経由する。

OCI の NAT Gateway には固定費がない。インターネット向けデータ転送料のみが課金対象で、OCI は月 10 TB まで無償（テナンシ全体の egress 合計に対する枠）のため、本アプリの規模ではコストは発生しない（詳細は Consequences 参照）。

### ルーティング設計

| ルートテーブル | 関連付け先 | ルール |
| -------------- | ---------- | ------ |
| パブリック用   | パブリックサブネット | `0.0.0.0/0` → Internet Gateway |
| プライベート用 | プライベートサブネット | `SERVICE_CIDR_BLOCK`（All \<region\> Services in Oracle Services Network）→ Service Gateway<br>`0.0.0.0/0` → NAT Gateway |

プライベート用ルートテーブルには Service Gateway と NAT Gateway の両方を設定する。OCI のルート・ルールは**最長プレフィックス一致**で選択されるため、Oracle Services Network 宛（より限定的なルール）は Service Gateway、それ以外は NAT Gateway に自動で振り分けられる。

<!-- Docs: https://docs.oracle.com/en-us/iaas/Content/Network/Tasks/managingroutetables.htm -->

この結果として、以下の通信は NAT Gateway を経由しない:

- OCIR からのコンテナイメージ pull
- Vault からの Secret 取得
- Object Storage へのバックアップ転送
- Oracle Linux の yum リポジトリからのパッケージ取得

NAT Gateway を経由するのは Docker Hub、外部 API（Google OAuth のトークンエンドポイント等）、その他インターネット宛の通信のみ。

## Alternatives Considered

### OCIR に PostgreSQL イメージを事前プッシュして NAT Gateway を回避

- **不採用理由**:
  - OCIR への postgres ベースイメージの手動プッシュ・バージョン管理が運用負荷になる
  - postgres の公式イメージ更新のたびに OCIR への再プッシュが必要（CI に組み込むか手動か）
  - NAT Gateway の実費が無視できるレベル（実績では課金なし）であるため、運用複雑化より NAT GW を立てる方が合理的

### Container Instance / VM をパブリックサブネットに直接配置

- **不採用理由**:
  - インスタンスに直接インターネットからアクセス可能になり、セキュリティリスクが増加
  - LB を前段に置く意義が薄れる

## Consequences

### Positive

- 一般的な「LB はパブリック / アプリ・DB はプライベート」のパターンを踏襲しており、セキュリティ的にも素直
- Service Gateway は無料。OS パッチ・OCI 内サービス通信は引き続き Service Gateway 経由で課金ゼロ
- NAT Gateway が利用可能になることで、将来的な外部 API 連携も追加費用最小で対応できる

### Negative / Trade-off

- プライベートサブネットからインターネットへのアウトバウンド通信が発生する。NAT Gateway 自体の料金は OCI の価格表に項目がなく、Phase 7 Step 8 以降の実績でも NAT Gateway の課金は発生していない（請求は Block Storage のみ）。発生しうるのはインターネット向けデータ転送料のみで、OCI は月 10 TB まで無償（テナンシ全体の egress 合計）のため、個人アプリの規模では事実上ゼロ
- プライベートサブネットから任意のインターネット宛先に到達できる経路が生まれる。宛先制限はルートテーブルではなく NSG の egress ルールで行う必要があるが、**現状は egress を全許可としており、制限していない**（`postgres_vm` の DB NSG）。外部 API 連携を広げる予定があるため当面は許容するが、送信先を絞る必要が生じた時点で NSG で対応する

### Neutral

- VCN の CIDR は将来的にサブネットを追加できるよう /16 で確保しておく

## 実装記録

- **実装**: Phase 7 Step 8（2026-05-13）。`modules/network/` に NAT Gateway を追加し、private ルートテーブルに `0.0.0.0/0 → NAT Gateway` を設定
- **コスト検証**: 2026-10-10。Cost Analysis の Usage ビュー（2026-09-25〜10-09、テナンシー全体、日次）で確認

検証結果:

- **NAT Gateway の SKU 行が存在しない**。固定費・時間課金ともに計量されていない
- `Virtual Cloud Network / Outbound Data Transfer Zone 2` は 1 日あたり約 0.003 GB 月（月換算 約 0.09 GB）。テナンシ全体で月 10 TB まで無償のため課金は発生しない
- 2026-09-25 以降、課金が発生しているサービスは Block Storage のみ。日額は約 11 円で一定であり、Step 9 の apply（2026-10-04）を挟んでも変動していない

Step 8 で「NAT Gateway 月額 約 $22」と見積もったが、この数字には裏付けがなく誤りだった（2026-10-04 に撤回）。上記のとおり実績でも課金は発生していない。
